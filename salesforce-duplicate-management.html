Salesforce duplicate management: matching rules that actually work

Most orgs don’t have a duplicate problem because they skipped duplicate management. They have one because they turned on the defaults, got burned, and switched it off.

In this note

A sales ops lead at a mid-size company once told me, “We tried duplicate rules. They blocked half our web leads, so we turned them off.” That was three years earlier. Their Account object had the same customer under four spellings, routing sent renewals to new-business reps, and the board deck counted one logo as three.

Duplicate management in Salesforce is the combination of matching rules, which define when two records are the same, and duplicate rules, which decide what happens when they are. Duplicate jobs and merge tools clean up what already exists. Get the matching wrong and everything downstream, from alerts to reports to blocking, inherits the mistake.

I’ve spent 12 years in Salesforce orgs from 200 users to more than 60,000, including M&A transitions where two companies’ customer lists landed in one org on the same weekend. The pattern is consistent: the teams that win at duplicates spend most of their effort on matching rules and very little on the duplicate rule settings everyone argues about. This note is how I build matching rules that hold up.

Matching rules, duplicate rules, and duplicate jobs

Three features do three different jobs, and most confusion starts when people treat them as one:

  • Matching rule The comparison logic. Which fields to compare, whether each uses an exact or fuzzy method, and how criteria combine with AND/OR. It finds candidates and does nothing else.
  • Duplicate rule The policy. When a matching rule finds a candidate, the duplicate rule decides whether to allow the save with an alert, block it, and whether to log the match in a duplicate record set for reporting.
  • Duplicate job The backlog scan. Runs a matching rule across existing records and groups the results into duplicate record sets so someone can merge them. Available in Performance and Unlimited Editions.
  • Merge The resolution. Combines up to three records at a time in the UI, keeps the master record, and reparents related records. This is where survivorship decisions live.

The limits shape the design. You can have up to five active duplicate rules per object and up to five active matching rules per object, and each duplicate rule can reference up to three matching rules, one per object. Five sounds like plenty until you write one rule per data source.

Why the standard matching rules miss real duplicates

Salesforce ships standard matching rules for Accounts, Contacts, and Leads, and they’re a reasonable demo. In production they fail in two directions at once.

  • They miss obvious duplicates The standard rules lean on name plus one more field. A contact with the same email but a nickname and a different phone number can slip through, and an account entered as the website domain instead of the legal name rarely matches.
  • They over-match common names Two different people named Michael Chen at two offices of the same customer look identical to a name-plus-company rule. Reps learn that alerts are noise and click past every one.
  • They ignore how your data arrives Marketing automation, enrichment tools, imports, and integrations each shape names and addresses differently. A rule tuned for hand-typed records breaks on synced ones.
  • They can’t see your normalization Fuzzy methods only exist for common standard fields. Any custom field you rely on, such as an external ID or a cleaned domain, can only match exactly, so it has to be clean before the rule sees it.
“A matching rule that cries wolf is worse than no rule. Reps stop reading alerts, and then they stop trusting the data.”

How a Salesforce matching rule actually decides

A matching rule is a set of field criteria. Each criterion compares one field with one matching method. The rule matches when its filter logic evaluates true, for example (1 AND 2) OR 3. Salesforce builds match keys from the rule’s fields to find candidates quickly, then scores each candidate field by field.

Exact matching compares the values as entered, so the field has to be clean before the rule sees it. Fuzzy matching runs one or more algorithms and keeps the best score against a threshold. These are the fuzzy methods and what they’re good at:

// Fuzzy matching methods in Salesforce matching rules
MethodAlgorithmsThresholdUse it for
First NameExact, Initials, Jaro-Winkler, Name Variant85Bob vs. Robert, J. vs. John
Last NameExact, Keyboard Distance, Metaphone 390Typos and sound-alikes
Company NameAcronym, Exact, Syllable Alignment70IBM vs. International Business Machines; drops Inc, Corp
PhoneExact, Weighted Average80Formatting differences; best on North American numbers
StreetExact, Weighted Average80St vs. Street, suite noise
CityEdit Distance, Exact85Misspelled city names
ZIPExact, Weighted Average80ZIP+4 vs. five-digit ZIP
TitleAcronym, Exact, Kullback-Liebler Distance50VP vs. Vice President

Two settings matter more than the algorithms:

  • Match blank fields Each criterion has a checkbox for whether two blank values count as a match. Leave it off almost everywhere. With it on, two leads with no phone and no company can match each other on name alone.
  • Filter logic The default is AND across all criteria, which is too strict. Write the logic as alternate paths to a match: strong single signals OR combinations of weaker ones. That’s how humans recognize duplicates.

Fuzzy matching on Company Name has the lowest threshold of the set, so it casts the widest net. Always pair it with something that narrows the match, like country, postal code, or domain.

Design rules from your real duplicates, not the defaults

The fastest way to a good rule is to stop guessing. Before I open Setup, I pull a sample of duplicates that people have already merged or flagged, usually around 200 pairs, and sort them by why a human knew they were the same.

  • Same email Usually the biggest bucket for Leads and Contacts, and the cleanest signal, once you exclude shared inboxes like info@ and sales@.
  • Name variants Nicknames, initials, maiden names, and typos with the same company. Fuzzy first and last name handle these well.
  • Same domain For Accounts, the website or email domain beats the company name. Legal names, brand names, and abbreviations all collapse to one domain.
  • Same phone or address Weaker on their own, since offices share switchboards. Good as a second signal next to a fuzzy name.
  • System-made Two integrations creating the same record minutes apart. The fix here is usually upsert on an external ID, not a matching rule.

Then write one criterion path per bucket, and test the draft rule against a second sample of known non-duplicates, such as two contacts at the same account with similar names. A rule that catches 90% of the first sample and flags almost nothing in the second is ready for production. In my experience, the first draft rarely is.

Matching rule recipes that work

These are the starting points I adapt in most orgs. Adjust them to your buckets, but notice the shape: every rule has a strong exact path and a fuzzy path that’s narrowed by a second field.

Accounts: match on domain first

Company names are the worst field in most CRMs. Add a text field for the normalized website domain, populate it in a before-save record-triggered Flow, and match on it exactly. Formula fields aren’t the right tool here, because you want a stored, clean value any rule or integration can use.

// Flow formula: normalized website domain (store in Website_Domain__c)
LEFT(
LOWER(SUBSTITUTE(SUBSTITUTE(SUBSTITUTE({!$Record.Website}, "https://", ""), "http://", ""), "www.", "")),
FIND("/", LOWER(SUBSTITUTE(SUBSTITUTE(SUBSTITUTE({!$Record.Website}, "https://", ""), "http://", ""), "www.", "")) & "/") - 1
)
// Account matching rule: domain or name + location
1 Website_Domain__c Exact match blank: off
2 BillingCountry Exact match blank: off
3 Name Fuzzy: Company Name
4 BillingPostalCode Fuzzy: ZIP match blank: off
Logic: (1 AND 2) OR (3 AND 2 AND 4)

Country in the domain path keeps a global parent’s regional subsidiaries apart if your data model treats them as separate accounts. If it doesn’t, drop criterion 2 from the first path.

Contacts and Leads: email, then name with a second signal

// Contact matching rule: email or name + account/phone
1 Email Exact match blank: off
2 FirstName Fuzzy: First Name
3 LastName Fuzzy: Last Name
4 Account Name Fuzzy: Company Name match blank: off
5 Phone Fuzzy: Phone match blank: off
Logic: 1 OR (2 AND 3 AND 4) OR (2 AND 3 AND 5)

On the duplicate rule, add a condition that skips records whose email starts with role addresses such as info@, sales@, or admin@, so a shared inbox doesn’t merge five people into one. The Lead version is the same rule with Company in place of Account Name.

Leads against Contacts: the rule most orgs never build

The most expensive duplicate isn’t two leads. It’s a new lead from someone who is already a contact on a customer account. Create a duplicate rule on Lead with two matching rules: the Lead rule above, plus a Lead-to-Contact rule that maps Lead Email to Contact Email and Lead Company to Account Name. Reps see the existing contact before they work the lead, and lead routing can send it to the account owner instead of round-robin.

Custom objects

Matching rules work on custom objects, but only with exact matching, so the work moves upstream. Normalize the key fields with a before-save Flow (trim, lowercase, strip punctuation) and match on the cleaned values. If an external system owns the record, an external ID with upsert prevents duplicates far better than any rule.

Duplicate rules: alert, report, or block

A duplicate rule has two actions, one for create and one for edit: Allow or Block. Allow can show an alert, and either can log the match with Report, which writes a duplicate record set you can query and report on. You can also skip a rule with conditions on the current user, such as profile or role, which is how you exempt an integration user without exempting everyone.

I roll out every rule in the same order:

// Duplicate rule rollout sequence
PhaseActionWhat you’re learningExit criteria
1. ObserveAllow, no alert, Report onVolume and false positives, invisible to usersTwo to four weeks of sets reviewed
2. AlertAllow, Alert on, Report onWhether reps act on alertsFalse positives rare in review
3. Block (selectively)Block on create for internal UI entryWhether blocking stops real duplicatesNo legitimate records rejected

Block is a scalpel, not a default. I block on internal manual entry for Accounts once the domain rule is proven. I almost never block Leads, because a returning buyer isn’t an error, and a blocked form submission is a lost buyer you’ll never hear about.

The entry points that skip your rules

Most “our duplicate rules don’t work” tickets are really “our duplicate rules never ran.” Duplicate rules don’t run in these cases:

  • Quick Create and self-registration Records created with Quick Create or through Experience Cloud self-registration skip duplicate rules.
  • Lead conversion Conversion doesn’t run duplicate rules unless Use Apex Lead Convert is enabled in Lead Settings.
  • Undelete and manual merge Restoring records from the Recycle Bin and merging records don’t run duplicate rules.
  • Lightning Sync Contacts created by Lightning Sync aren’t checked against duplicate rules.

API loads and integrations are the other blind spot. An alert is a UI conversation, and over the API there’s nobody to click “Save anyway.” A blocking rule returns a DUPLICATES_DETECTED error, and an integration can send DuplicateRuleHeader with allowSave set to true to save through alerts. In Apex the same switch lives on Database.DMLOptions.

Because behavior depends on the API, the header, and the tool, I don’t trust documentation or vendor claims here. In a sandbox, push one known duplicate through every integration and every import path, and write down what happened. That one afternoon tells you more than any setting page, and it surfaces the code that quietly sets allowSave to true.

Cleaning up the duplicates you already have

Rules stop new duplicates. They don’t fix the ones you have. For the backlog:

  • Run duplicate jobs In Performance and Unlimited Editions, duplicate jobs scan existing records with a matching rule and create duplicate record sets. On custom objects you can run jobs but not compare and merge from the results.
  • Merge by priority Start with accounts that have open opportunities or active contracts, then contacts in active sequences. Merging dead records first feels productive and changes nothing.
  • Decide survivorship first Write down which record wins and which field values survive: oldest record, most activity, or the one tied to billing. Merging without rules overwrites good data with bad.
  • Know when to buy a tool Native merge handles three records at a time. For tens of thousands of duplicates, mass merges with survivorship rules, or cross-object cleanup, tools like DemandTools, Plauti Duplicate Check, or Cloudingo pay for themselves.

Fix the source before you clean. If one integration created 80% of the duplicates, merging them before fixing it just schedules the next cleanup.

How to measure duplicate management

Turn on Report in every duplicate rule, even before alerts. The duplicate record sets it writes are the data you need to tune rules and prove progress.

// Duplicate sets created per rule, last 30 days
SELECT DuplicateRuleId, COUNT(Id) sets FROM DuplicateRecordSet
WHERE CreatedDate = LAST_N_DAYS:30 GROUP BY DuplicateRuleId
// Open duplicate sets waiting on a merge decision
SELECT Id, Name, DuplicateRuleId, RecordCount, CreatedDate FROM DuplicateRecordSet
WHERE RecordCount > 1 ORDER BY CreatedDate ASC

Report four numbers to whoever owns data quality:

  • Duplicate rate Share of active Accounts and Contacts that sit in an open duplicate set. Trend it monthly.
  • False-positive rate Of a reviewed sample of sets, how many weren’t real duplicates. This is the number that tells you whether a rule is ready to alert or block.
  • Time to merge Age of open duplicate sets. If it only grows, nobody owns the queue.
  • New duplicates by source Sets created per week by lead source or created-by user. It points straight at the integration or import that needs fixing.

These belong on the same dashboard as fill rates for your critical fields. If nobody reviews it weekly, the numbers drift back. That’s the data stewardship habit, and duplicate management doesn’t last without it.

A 30-60-90 day duplicate management plan

  1. Days 1–30 Pull 200 known duplicate pairs and bucket them. Map every entry point: UI, imports, integrations, and forms. Add the normalized domain field and backfill it. Deactivate rules that block without reporting.
  2. Days 31–60 Build the Account, Contact, Lead, and Lead-to-Contact matching rules. Run duplicate rules on Report only, review sets weekly, and tune until false positives are rare. Test every integration with a known duplicate in a sandbox.
  3. Days 61–90 Turn on alerts, then block internal Account entry if the data supports it. Run duplicate jobs and merge by priority with written survivorship rules. Publish the duplicate dashboard and assign a weekly owner.

Clean, matched records are what everything else stands on, from routing to forecasting to AI. If you’re heading toward Agentforce, duplicate accounts are one of the first things that will embarrass an agent in front of a customer; I cover that in data readiness for AI. And if your org has years of half-finished rules, start with a tech debt audit.

Frequently asked questions

What is the difference between a matching rule and a duplicate rule in Salesforce?

A matching rule defines how two records are compared: which fields, and whether each uses exact or fuzzy matching. A duplicate rule decides what happens when a matching rule finds a match: allow with an alert, block the save, and whether to log the match for reporting. A duplicate rule can use up to three matching rules.

How many matching rules and duplicate rules can be active in Salesforce?

Salesforce allows up to five active duplicate rules per object and up to five active matching rules per object. Each duplicate rule can reference up to three matching rules, one per object, which is how a Lead rule can also check Contacts.

Should I use exact or fuzzy matching?

Use exact matching on fields that are already standardized or that you normalize yourself, such as email, a cleaned website domain, or an external ID. Use fuzzy matching on human-typed names, company names, and addresses. Fuzzy methods only exist for common standard fields, so custom fields match exactly.

Should a duplicate rule block or alert?

Start every new rule on Allow with Alert and Report turned on. Review the duplicate record sets it creates for a few weeks and measure the false-positive rate. Move a rule to Block only when its matches are almost always real duplicates, and never block inbound lead sources like Web-to-Lead.

Why didn’t my duplicate rule fire?

Duplicate rules don’t run on Quick Create, Experience Cloud self-registration, Undelete, manual merges, or records added by Lightning Sync. They don’t run on lead conversion unless Use Apex Lead Convert is enabled. API loads and integrations behave differently from the UI, so test each one in a sandbox.

Can Salesforce match Leads against Contacts?

Yes. Create a duplicate rule on Lead and add a second matching rule that compares the Lead to Contacts, mapping fields like email, first name, last name, and company to account name. Reps then see an existing contact before they work a new lead from the same person.
